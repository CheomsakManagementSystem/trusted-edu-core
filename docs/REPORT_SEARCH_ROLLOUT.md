# 리포트 검색 인덱스 배포

## 변경 요약

- 검색 시 전체 리포트를 내려받지 않고 `searchTokens` 복합 인덱스로 현재 페이지와 다음 페이지 확인용 1건만 조회한다.
- 미연결 목록은 최대 31건, 보관함은 최대 51건을 먼저 받아 바로 렌더링한다.
- 총 건수 집계는 결과 렌더링 뒤 비동기로 실행한다.
- 검색 입력은 120ms 디바운스하고, 이전 검색의 늦은 응답은 화면 상태에 반영하지 않는다.

## 배포 순서

검색 코드를 먼저 배포하면 기존 문서에 `searchTokens`가 없어 결과가 누락될 수 있다. 아래 순서를 지킨다.

1. 복합 인덱스를 배포하고 Firebase Console에서 모두 `Ready` 상태가 될 때까지 기다린다.

   ```bash
   firebase deploy --only firestore:indexes
   ```

2. 운영 프로젝트 자격 증명이 연결된 환경에서 백필을 먼저 dry-run 한다.

   ```bash
   npm --prefix functions run backfill:report-search
   ```

3. 출력의 `scanned`, `matched`, `averageTokens`, `maxTokens`를 확인한 뒤 적용한다.

   ```bash
   npm --prefix functions run backfill:report-search -- --apply
   ```

4. 같은 dry-run을 다시 실행해 `matched: 0`인지 확인한다.

5. 자동 매칭 함수를 배포한 뒤 기존 웹 배포 절차로 프런트엔드를 배포한다.

   ```bash
   firebase deploy --only functions:autoMatchPendingReports
   ```

## 예상 성능

| 구간 | 기존 | 변경 후 | 예상 감소 |
|---|---:|---:|---:|
| 미연결 1,900건 검색 결과 첫 표시 | 약 1,900개 문서 수신 후 브라우저 필터 | 최대 31개 문서 수신 | 문서 수신량 약 98.4% 감소 |
| 보관함 N건 검색 결과 첫 표시 | N개 문서를 100개씩 순차 수신 | 최대 51개 문서 수신 | `1 - 51/N` |
| 브라우저 검색 연산 | O(N) | O(30) 또는 O(50) | 데이터 증가 영향 제거 |
| 검색 왕복 횟수 | 미연결 1회 대용량, 보관함 `ceil(N/100)`회 | 결과 1회 + 비차단 집계 1회 | 첫 결과는 1회 |

1,900건 기준 문서 수신량 계산은 `(1,900 - 31) / 1,900 = 98.37%`다. 실제 체감 시간은 문서 크기, Firestore 리전, 사용자의 네트워크에 좌우되므로 배포 후 `admin_pending_load`, `admin_published_load`, `admin_published_search`의 p50·p95를 이전 빌드와 비교한다.

## 비용과 제약

- 백필은 기존 리포트 수만큼 최대 한 번의 문서 쓰기를 만든다.
- 이후 리포트 생성, 학생 재배정, 첨삭자 수정 시 검색 토큰도 함께 갱신된다.
- 토큰은 문서당 최대 480개로 제한해 Firestore 인덱스 엔트리 증가를 통제한다.
- 24자를 넘는 긴 값은 전체 값과 제한된 부분 문자열만 보장한다. 학생 이름과 일반적인 파일명·논제 검색은 부분 문자열로 검색된다.
